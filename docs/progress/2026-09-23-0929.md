## 1. Where the project actually is

A working, tested Tool Gateway, plus five narrow slices of the platform
around it. An agent can point at `helmdeep-gateway` as its MCP server,
get allowed or denied by real Rego policy, and a stranger can verify the
resulting audit chain — Phase 1's exit criterion in `ROADMAP.md`, met.

Everything past that is deliberately narrow: of the 16 numbered design
documents in `docs/`, **not one is fully implemented**. Seven are
partial, two are interface-only stubs, two have no code at all, four
aren't implementation documents, and one is out of scope by design. The
gap between "what the design describes" and "what runs" is the main fact
this report exists to keep honest.

## 6. Known debt worth naming

- **`replicas: 1` is a correctness constraint, not a default.** The rate
  limiter and provenance cache are in-process. Scaling out silently
  changes what a rate limit means. Blocks any real availability story.
- **The ledger is one file on one disk.** Tamper-*evident*, not
  tamper-proof, and not off-cluster. A compromised gateway process can
  forge a self-consistent chain from that point forward.
- **Bundle signing is opt-in.** A deployment that doesn't set
  `policy.signature` — including `deploy/k8s` as shipped — is exactly as
  exposed as before ADR 0014.
- **The human hop in a delegation chain is asserted, not verified.**
  There is no real IdP to verify it against, so `DelegationChain` is
  always empty and T10 coverage is thinner than the field suggests.
- **No component-level threat model.** `docs/threat-model.md` has been a
  placeholder since the repo started.

## 7. Next

`ROADMAP.md` leaves Phase 4 (agent sandbox) and Phase 5 (scheduler) as
the two large unopened areas. Two smaller, already-scoped slices sit in
front of them:

1. **`log_only` shadow mode** — small, self-contained, ~8 outcome
   comparison sites; the one item on doc 09 §2.3's list that doesn't
   need a component that doesn't exist.
2. **`policy test` + dry-run against the ledger** — larger; the real
   work is a read API for `pkg/audit` and deciding whether
   `types.ActionRecord` should start carrying `DecisionContext` (without
   it, limit-type policies can't be replayed faithfully).

Trust Engine stays deliberately unattempted: doc 09 §1.1 warns a naive
promotion rule is "the most likely way this feature fails in
production," and its real inputs (Approval Service, Eval Service) don't
exist to derive one honestly from.
